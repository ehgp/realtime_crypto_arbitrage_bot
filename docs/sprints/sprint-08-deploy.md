# Sprint Guide 08 — Deploy (Phase 8)

**Preconditions**: Phase 7 gate green; human-todo H-DNS, H-NEON, H-TUNNEL, H-VERCEL done (domains, Neon prod project + roles bootstrapped, tunnel created, Vercel project linked).
**Phase exit gate**: cloudaitrader.com serves authed traffic via backend.cloudaitrader.com; Backtester on the Pi completes a real user Backtest; Stripe live webhook registered and verified.

## Sprint 8.1 — compose-host on the Pi fleet

- `docker-compose-host.yml`: services `backend` + `backtester` (+ `migrate` one-shot, profile `migrate`). No postgres/pgadmin, no published ports for backtester; backend exposes `4000` on the compose network only. Deploy script runs `docker compose -f docker-compose-host.yml run --rm migrate` FIRST (D14: `--rm` disposes the container and its DIRECT_URL env — Neon pooler breaks DDL so migrate uses the direct owner URL), then `up -d` the runtime services, whose env carries ONLY `DATABASE_URL` + `SERVICE_DATABASE_URL` (backend) and `WORKER_DATABASE_URL` (backtester) — never DIRECT_URL.
- Images: multi-arch build (`linux/arm64` for Pi) — `docker buildx` targets in a `build.sh`; `node:24.22.1-slim` and `python:3.12-slim` bases both publish arm64.
- Manual bootstrap (documented header): run ALL THREE role files — `000_role.sql`, `000_worker_role.sql`, `000_service_role.sql` — once against Neon as owner with generated passwords via psql variables (H-NEON/H-NEON-2, R9-9); verify all four identities (`SELECT current_user` per DSN) before the first migration.
- Pi selection + capacity check per eg-pi-ops conventions (worker is CPU-bound during Backtests; pick the Pi with SSD boot + least load; do NOT reboot without asking).
- Watchdog: `restart: unless-stopped` on both services.

## Sprint 8.2 — Vercel web tier

- Vercel project → `app/frontend` root; domains: cloudaitrader.com + www redirect (H-DNS/H-VERCEL).
- Env (Production): all `AUTH0_*`, `APP_BASE_URL=https://cloudaitrader.com`, `API_BASE_URL=https://backend.cloudaitrader.com`, `NEXT_PUBLIC_TURNSTILE_SITE_KEY`, Sentry DSNs, `NEXT_PUBLIC_` analytics defaults.
- Auth0 app callback/logout URLs add production origins (H-AUTH).
- Stripe: switch webhook endpoint to `https://backend.cloudaitrader.com/stripe/webhook` (live mode, H-PAY); verify with `stripe trigger` against live-mode test clock or a $0 coupon flow.

## Sprint 8.3 — Backend named tunnel (backend only — D5)

- `infra/tunnel/`: `tunnel-up.sh` + `tunnel-up.ps1 [backend]` starting a profile-gated `cloudflared-backend` service (compose overlay `docker-compose.tunnel.yml`, profile `tunnel`). **Interface: TOKEN mode only** (dashboard-created named tunnel; CLI-login mode dropped for headless Pi operation). The atomic consumed set (enters `.env.example` + the PLAN inventory in this sprint): `BACKEND_TUNNEL_TOKEN` (consumed by the cloudflared connector), `BACKEND_TUNNEL_HOSTNAME=backend.cloudaitrader.com` (consumed by the script's post-start verification `curl -sf https://$BACKEND_TUNNEL_HOSTNAME/health`), `BACKEND_TUNNEL_NAME=cloudaitrader-backend` (consumed as the compose service/log label and the dashboard tunnel name the script asserts in `cloudflared tunnel info` output). Route target `http://backend:4000` over the compose network; no inbound ports on the Pi, no `depends_on` (cloudflared retries origin).
- Worker tunnel intentionally ABSENT: assert in script that `[worker]` argument exits with "reserved, not provisioned (PLAN.md D5)".
- Backend CORS: allow origin `https://cloudaitrader.com` only; Helmet on; trust proxy 1 (Cloudflare) so `remoteip`/rate limits see real IPs.

## Sprint 8.4 — DB fallback (Format B inv 17)

**Deliverables include `infra/fallback/RUNBOOK.md` + `infra/fallback/{sync.sh,cutover.sh,failback.sh,operator-env.sh}` + `infra/operator.env.example`** — the runbook is the procedural source of truth encoding the PLAN's fallback invariants (R14-1..9): temporary read-write endpoint creation + `template0` database recreation on the staging branch before any restore; a durable pre-POST failback journal with restart reconciliation against the live branch listing and crash-boundary tests at POST/poll/persist; the shared whole-run lock held across failback with CAS on promotion state + resolved branch id before destructive steps; a failback epoch gate identical in strength to cutover (fresh uuid on validated staging; all primary DSNs equal it; all fallback DSNs differ); logged sign-off deletion of recovery-1 before the second drill restore (three-state storage budget); and the full sync-marker field set (`snapshot_started_at`, `validated_at`, source project/branch/LSN/epoch, fallback generation) validated field-by-field at cutover.

- `docker-compose.fallback.yml` on **eg-server-3**: `postgres:17` with a persistent volume, port published ONLY on the fleet/WireGuard interface (10.189.1.x bind, never 0.0.0.0); compose `POSTGRES_*` superuser is bootstrap-only — neither worker ever connects as it.
- Bootstrap: the operator scripts source `operator-env.sh` and run the three `000_*` role files (`\prompt -s` passwords) + `docker compose run --rm migrate`, passing `FALLBACK_DIRECT_URL` TRANSIENTLY as `DIRECT_URL` to that one-shot run (documented mapping, R16-2 — the migrate job only ever knows the name `DIRECT_URL`).
- Env, least-privilege subsets (R9-3, domains R16-2): backend gets `DATABASE_URL`/`SERVICE_DATABASE_URL` + their `FALLBACK_*` mirrors + `DB_ACTIVE`; backtester gets `WORKER_DATABASE_URL` + `FALLBACK_WORKER_DATABASE_URL` + `DB_ACTIVE`. Atomic entry here: those FOUR runtime vars → `.env.example`; `FALLBACK_DIRECT_URL` → `infra/operator.env.example` (operator domain). Loaders select the active set per `DB_ACTIVE` and throw if the selected set is unset.
- Warm sync under ONE exclusion lock (R10-1, promotion-check R11-1): the sync script takes `flock /var/lock/cloudaitrader-db.lock` for its ENTIRE run and, FIRST thing after acquiring it, reads durable promotion state — active ≠ `primary` → exit + admin alert (tested on the first scheduled run after promotion); then recreate staging FRESH (`dropdb --if-exists cloudaitrader_staging && createdb -T template0 cloudaitrader_staging` — R13-2, restores never hit a populated target) → `pg_dump -Fc --no-owner --no-acl` STREAMED into `pg_restore --no-owner --no-acl --exit-on-error` (no plaintext dump file, R10-8/9) → **re-run `005_grants.sql` (the single-source grants migration — there is no separate grants script)** → **run `verify_roles.sql` (full verb/RLS/ownership matrix; login-only probes don't count — R12-2)** → atomic swap (rename) → **stamp the durable `last_validated_sync` marker (timestamp + source identity — R13-4)**; alert when marker age > RPO + grace. The cutover script acquires the SAME lock before writing durable promotion state — an in-flight sync and a cutover cannot interleave. Interval = accepted RPO (default 6h, H-FALLBACK-1); health check alerts on Neon unresponsiveness. Drill includes TWO consecutive warm-syncs.
- **Cutover is manual and split-brain-proof (R10-4, expected-epoch R11-5, staleness-gated R13-4)**: under the lock — REFUSE if `last_validated_sync` age > RPO + grace unless the operator passes an explicit, logged `--override-stale` after adjudication → STOP BOTH workers → generate an expected transition uuid and stamp it ONLY on the fallback's `app.db_epoch` → write durable promotion state + flip `DB_ACTIVE=fallback` → every selected DSN must return EXACTLY the expected uuid AND the Neon probe passes tri-state (matching epoch = FAIL/miswire; different = PASS; UNREACHABLE = PASS only with fresh uuid + validated fallback-generation identity proven on all selected DSNs — a dead Neon must never block activation, R15-1) → start both (`up -d --force-recreate`); any failure = start neither, roll back as a unit. Write failover is NEVER automatic. Acceptance includes a complete-Neon-outage cutover case.
- **Failback runbook (R10-2/3, executable)**: (1) stop both workers; (2) DIVERGENCE analysis old-Neon vs fallback — every authoritative table, `schema_migrations` version, sequence values, manifest fields — operator adjudicates before proceeding; (3) create a FRESH Neon staging branch (delete any prior one — R13-2), dump fallback → restore into it, then `005_grants.sql` → fidelity check fallback vs staging (full counts/hashes) → `verify_roles.sql` matrix against staging (R12-2); (4) **promote via the Neon Restore Branch API** (`POST .../branches/{NEON_PRIMARY_BRANCH_ID}/restore` with `source_branch_id` = staging AND `preserve_under_name: "recovery-<ts>"` — required once the target has children; retain the recovery branch until sign-off; POLL EVERY returned operation to terminal success; the restore yields a NEW branch id — atomically persist it as the refreshed `NEON_PRIMARY_BRANCH_ID` in the operator env file; never blind-retry an ambiguous POST; DSN endpoints unchanged — R13-1); (5) verify the expected transition `db_epoch` (stamped on staging pre-restore) through every primary DSN; flip `DB_ACTIVE=primary`, start both; failure semantics (R15-3): pre-POST failures abort freely (stay on fallback); post-commit validation failures keep the fallback ACTIVE while journal-led reconciliation determines the real Neon state — re-attempt promotion or deliberately adopt the recovery branch, never a pretend-rollback; (6) delete the staging branch, clear promotion state under the lock, re-enable sync. The drill proves TWO consecutive restores.
- **Data protection (R10-9)**: fallback volume on a LUKS-encrypted partition; credential files 0600; any retained dump age-encrypted, retention 2, secure-deleted; host patch cadence + SSH access audit folded into Sprint 9.1.
- **Drill once**: full cutover + deliberate overlapping-sync test (lock serializes; no clobber) + failback with transcripts.

### Acceptance (8.4 — every item explicit, R14-5)
- Fallback port unreachable from a non-fleet network (nmap from outside WireGuard); reachable from eg-server-N.
- TWO consecutive warm-syncs pass, each ending with `005_grants.sql` + `verify_roles.sql` transcripts and a fully-populated `last_validated_sync` marker (all fields).
- Cutover: stale-marker refusal demonstrated (aged marker → refusal; `--override-stale` path exercised once and audit-logged); expected-epoch check passes; post-promotion first-cron sync-refusal shown.
- Failback: TWO consecutive restores — the second using the REFRESHED `NEON_PRIMARY_BRANCH_ID` persisted by the first (asserted in transcript); recovery-1 deleted with logged sign-off before restore two; failback epoch gate transcript (primary DSNs = fresh uuid, fallback DSNs differ); crash-boundary test transcript (POST/poll/persist injection).
- `infra/fallback/RUNBOOK.md` exists and matches the executed transcripts; sync cron visible in `crontab -l`; `cryptsetup status` shows the encrypted volume; no `*.dump`/`*.sql` plaintext artifacts post-cycle; runtime containers' env contains no `NEON_*` operator vars (`docker inspect`).
